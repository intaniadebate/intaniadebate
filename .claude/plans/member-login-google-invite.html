Club members sign in with Google, and only invited emails get in

Members and admins of Intania Debate Club sign in to the website with their Google account. An admin keeps the whitelist (the invite list) and decides who is an admin and who is a member. The public pages stay exactly as they are for every visitor.

1Admin adds an email to the invite list
2Member opens /login
3Member taps “Sign in with Google”
4Site checks the invite list
5Member sees /account with their role

Words used in this plan

Static site
Every page is a finished HTML file made at build time. The server only hands out files. It cannot ask “who are you?”, so it cannot have a login.
Server route
A page that runs code on each request. It can read a cookie, look up the user, and decide what to send back.
Session cookie
A random ID the browser stores after sign-in. The browser sends it with every request. The server looks it up in the database to know who you are.
OAuth (Google sign-in)
Google checks the password, not us. Google tells our server “this is somebody@gmail.com, and the email is verified”. We never store passwords.
Better Auth
An open-source TypeScript library that does sign-in, sessions and roles on our own server and database. Version 1.7.12 is current (released 2026-10-20).

What the club has today: one static site, zero logins

0 logins · 0 server routes

The site is built by Astro with output: 'static' (web/astro.config.mjs:6) and published by .github/workflows/pages.yml to GitHub Pages. GitHub Pages only serves files. Better Auth, and any other login that checks a role on the server, needs two things the club does not have yet: a place to run server code and a database.

Why A over B

A and B use the same Better Auth code and the same database. B keeps the public site untouched, but it costs a second project, a second deploy, and pages that hide data with browser JS. A keeps one project: /account and /admin check the role on the server before any HTML leaves. Cloudflare serves the static pages for free with no request limit, so the public pages cost nothing extra. The one risk in A is the DNS move, and slice 1 does that alone, with no login code, so it is easy to undo.

Task 2 — Add Better Auth with Google, the invite hook and D1

Create the D1 database intaniadebate-auth and bind it as DB. The migration holds the Better Auth tables (generated with npx @better-auth/cli generate, including the admin plugin columns role, banned, banReason, banExpires) plus member_invite. auth.mjs configures Google only, with prompt: "select_account". Its databaseHooks.user.create.before rejects any email without an invite, sets role from the invite, and deletes the invite after creation. The rule not to miss: the hook is the only gate. Leave emailAndPassword off, so no other path can create a user. docs/MEMBER_LOGIN.md lists the Google OAuth client steps (redirect URI https://intaniadebateclub.com/api/auth/callback/google), the secrets BETTER_AUTH_SECRET, GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET set with wrangler secret put, and the first-admin SQL.
