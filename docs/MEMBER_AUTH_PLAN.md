# แผนระบบสมาชิกและโหวต — ฉบับย่อ

แผนสำหรับรีวิว · 22 ตุลาคม 2026 · [PR #31](https://github.com/intaniadebate/intaniadebate/pull/31) · [Issue #30](https://github.com/intaniadebate/intaniadebate/issues/30)

**เอกสารภาพรวมนี้คงเป็น public ได้** เพราะไม่มีข้อมูลสมาชิกจริง กุญแจลับ หรือขั้นตอนกู้ระบบที่อ่อนไหว การรู้ชื่อโปรแกรม/ผังระบบไม่ควรทำให้ข้ามสิทธิ์ได้ ส่วนโค้ดสมาชิกและคู่มือปฏิบัติละเอียดจะอยู่ใน **private repo**; secrets และข้อมูลจริงไม่ลง Git แม้ repo จะ private

## 1. สอง repo เชื่อมกันอย่างไร

![ภาพระบบสอง repo และที่เก็บข้อมูล](diagrams/member-auth-system.svg)

| ส่วน | ใช้อะไร / ทำหน้าที่ |
| --- | --- |
| Repo public เดิม → เว็บหลัก | Astro + GitHub Pages เดิมที่ `intaniadebateclub.com`; เพิ่มปุ่มไปเว็บสมาชิก ไม่ย้ายทั้งเว็บหลัก |
| Repo private ใหม่ → เว็บสมาชิก | Astro บน Cloudflare Worker ที่เสนอให้ใช้ `members.intaniadebateclub.com`; เก็บโค้ดหน้า private, API, schema/migrations และคู่มือภายใน ให้สิทธิ์ repo เฉพาะทีมพัฒนา |
| Login | Google ยืนยันตัวตน → Better Auth ใน Worker ดูแล session → server ตรวจ verified email, invite และสถานะ; สมาชิกตั้งชื่อแสดงผลเองได้ ไม่รับรหัสผ่าน Gmail |
| ข้อมูล | D1 เก็บสมาชิก/ชื่อ/สิทธิ์/invite/session และรอบ/ผู้สมัคร/ผู้มีสิทธิ์/บัตรคะแนน/ผลรวม/audit; ทุกกิจกรรมผูก `user_id` ถาวร เปลี่ยนชื่อไม่เพิ่มสิทธิ์ |
| ไฟล์และสำรอง | R2 แบบ private เก็บ SQL backup และไฟล์แนบถ้ามี; ไฟล์ส่วนตัวอ่านผ่าน server ที่ตรวจสิทธิ์ ไม่มี public URL |

แต่ละ repo build/deploy แยกกัน ให้ Cloudflare เข้าถึงเฉพาะ private repo ที่เลือก; รุ่นแรกเว็บหลักเชื่อมด้วยลิงก์ ส่วนหน้า/API สมาชิกอยู่ subdomain เดียวกัน ใช้ cookie เฉพาะ host สมาชิก สมาชิกทั่วไปไม่ต้องมีสิทธิ์อ่าน GitHub repo

## 2. หน้าใหม่ที่ต้องทำ

ทุก path ด้านล่างอยู่บน **เว็บสมาชิก**; หน้ารายชื่อ `/members` บนเว็บหลักยังเป็นหน้าสาธารณะเดิม

| หน้า | เพื่ออะไร / ทำอย่างไร | ใครใช้ |
| --- | --- | --- |
| `/login` | กด Google login; ตรวจรายชื่ออนุญาตก่อนเข้า แสดงกรณีไม่ได้รับเชิญ/ถูกระงับ ไม่มีสมัครอิสระ | ทุกคนเห็นหน้าได้; เข้าเนื้อหาได้เฉพาะผู้มีสิทธิ์ |
| `/account` | ตั้ง/แก้ชื่อแสดงผล ดูบัญชีที่ผูก ออกจากระบบ และดาวน์โหลดข้อมูลตัวเองเป็น JSON | เจ้าของบัญชี |
| `/club` | หน้าหลักสมาชิก แสดงกิจกรรมและทางเข้าโหวต โดยตรวจ session ก่อนส่งข้อมูล | member/admin/owner ที่ active |
| `/club/elections` | ดูรอบโหวตและสถานะเปิด/ปิด เลือกรอบที่จะเข้า | สมาชิก |
| `/club/elections/:id` | แบ่งแต้มให้ candidate → ยืนยันบัตร; หลังปิดดูผลรวมและดาวน์โหลด CSV | สมาชิกดูผล; ส่งคะแนนเฉพาะรายชื่อผู้มีสิทธิ์ |
| `/admin` | ภาพรวมสมาชิก รอบโหวต และสถานะสำรองข้อมูล; ลิงก์ไปงานดูแล | admin/owner |
| `/admin/members` | เพิ่ม/ถอนอีเมลที่อนุญาต ระงับ/คืนสถานะ member; ส่วนแต่งตั้ง/ถอน admin/owner เปิดให้ owner เท่านั้น | admin/owner ตามขอบเขต |
| `/admin/elections/:id` | สร้าง/ตั้งรอบ candidate ผู้มีสิทธิ์ แต้ม เวลา → เปิดรอบ/กดหยุด → dashboard ผลรวมและรายคนหลังปิด | admin/owner |
| `/admin/data` | เลือกชุดข้อมูล/รอบและดาวน์โหลดรายงาน ดูเวลาสำรองสำเร็จล่าสุด; ไม่เปิด SQL backup ทั้งก้อนผ่านหน้านี้ | admin/owner |

## 3. เก็บและโหลดข้อมูลออกอย่างไร

**บันทึก:** หน้าเว็บ → API บน Worker ตรวจสิทธิ์/ข้อมูล → D1 → ยืนยันเมื่อเขียนสำเร็จเท่านั้น; browser ไม่เรียก D1 โดยตรง และไม่เก็บข้อมูลสมาชิกจริงใน HTML/JSON สาธารณะ

| ดาวน์โหลด | ใครได้ / ขอบเขต |
| --- | --- |
| JSON ข้อมูลตนเอง | เจ้าของบัญชี: โปรไฟล์และบัตรของตัวเอง ไม่รวม token/session secret |
| CSV ผลรวม | สมาชิก: เฉพาะรอบที่ปิดและสรุปเสร็จ ไม่มีชื่อผู้ลงคะแนน |
| CSV สมาชิก / บัตรคะแนนรายคน | admin/owner: รายชื่อเท่าที่จำเป็น และคะแนนรายคนเฉพาะหลังปิดรอบ; บันทึกผู้ดาวน์โหลด เวลา และขอบเขตใน audit |
| SQL backup ทั้งฐาน | ผู้ดูแลโครงสร้างพื้นฐานที่ได้รับสิทธิ์แยกต่างหาก ใช้สำรอง/กู้ระบบ ไม่ใช่รายงานสมาชิกทั่วไป |

ทุกการดาวน์โหลดตรวจสิทธิ์ใหม่ที่ server, ไม่ cache แบบ public, ไม่ส่งข้อมูล auth ลับในรายงาน และ CSV ต้องรองรับภาษาไทย/ป้องกันสูตรจากข้อความผู้ใช้ รายงานที่โหลดลงเครื่องแล้วต้องเก็บในพื้นที่จำกัดสิทธิ์; การถอนสิทธิ์เว็บไม่ลบไฟล์ที่เคยโหลดไป

**สำรองและกู้คืน (เสนอค่าเริ่มต้น):** GitHub Actions ใน private repo export D1 เป็น SQL → R2 private รายวัน และก่อนเปิด/หลังปิดรอบ; สำรองนอกช่วงรับโหวตเพราะ D1 export บล็อกคำขออื่นชั่วคราว เก็บ 30 วันแล้วลบตามนโยบายที่ทีมยืนยัน ใช้ token จำกัดสิทธิ์ใน Actions Secrets และแจ้งผู้ดูแลเมื่อสำรองไม่สำเร็จ ไม่แนบ SQL ใน repo/Actions artifacts สาธารณะ

D1 Time Travel ช่วยย้อนข้อมูลได้ 7 วันบน Free / 30 วันบน Paid ผู้ดูแลต้องซ้อม import SQL ลง staging ตรวจจำนวนสมาชิก/คะแนน/สิทธิ์ก่อนกู้จริง; การกู้ production ต้องมีแผนหยุดเขียนและถอน session เดิม ถ้ามีไฟล์แนบต้องสำรองไฟล์พร้อมรายการอ้างอิงแยกด้วย เพราะ SQL ไม่รวมไฟล์ R2

## 4. สิทธิ์และกติกาโหวต

- **member:** แก้ชื่อ/ข้อมูลตนเอง ดูส่วนสมาชิก; โหวตได้เมื่ออยู่ในรายชื่อของรอบ **admin:** ดูแล member และรอบโหวต **owner:** ทำงาน admin ได้และจัดการสิทธิ์ staff ห้ามทำให้ไม่เหลือ active owner; owner เว็บไม่เท่ากับผู้ดูแล GitHub/Cloudflare
- ผู้มีสิทธิ์แต่ละคนมีแต้มรวมเท่ากันต่อรอบ แล้วแบ่งให้ candidate จำนวนแต้มตั้งก่อนเปิด; role ไม่เพิ่มน้ำหนัก มีบัตรปัจจุบันหนึ่งใบต่อคนต่อรอบ server ตรวจงบและเวลาเสมอ ล็อกกติกา/candidate/ผู้มีสิทธิ์เมื่อเปิด
- admin/owner กดหยุดก่อนกำหนดได้ และถึง deadline ต้องหยุดรับเอง; ทดสอบส่งคะแนนพร้อมปิดรอบแบบ atomic ไม่รับบัตรครึ่งใบ/นับซ้ำ หลังปิดแก้บัตรไม่ได้ รอสรุปเสร็จจึงเผยผล
- สมาชิกเห็นผลรวมหลังปิด; admin/owner ดูรายคนได้ จึงต้องแจ้งก่อนโหวตว่า **ไม่ใช่การลงคะแนนนิรนาม** ข้อเสนอคือทุกคนไม่เห็นคะแนนระหว่างเปิด มีเพียงจำนวนผู้ส่งให้ผู้ดูแลดู

## 5. ลำดับลงมือทำและเกณฑ์จบ

| ระยะ | ทำอะไร / ผ่านเมื่อ |
| --- | --- |
| 1 — เตรียม | กำหนดทีม/owner สำรอง สร้าง private repo และ preview แยก DB/secrets จาก production; พิสูจน์ Astro adapter, OAuth, D1 และโควตาด้วยข้อมูลจำลอง |
| 2 — สมาชิก | ทำ login/account/club/admin/members พร้อม API; ทดสอบคนนอก/member/admin/owner รวม raw auth API, การระงับ/ถอน session, owner คนสุดท้าย และชื่อไทย |
| 3 — ข้อมูล | ทำหน้า data, JSON/CSV, audit และ backup; ทดสอบขอบเขตดาวน์โหลด ไฟล์ภาษาไทย สูตร CSV และกู้ SQL ลง staging ได้จริง |
| 4 — โหวต | ทำหน้ารอบ/บัตร/dashboard; ซ้อมสมาชิก 30 คน ส่งซ้ำ/เกินแต้ม/เลยเวลา/ปิดพร้อมส่ง ผลรวมตรงกับชุดคะแนนตรวจด้วยมือ |
| 5 — เปิดใช้ | review แต่ละ PR ตรวจ CI/backup/rollback จึงผูก subdomain และเพิ่มปุ่มในเว็บหลัก; ย้อนเฉพาะเว็บสมาชิกได้โดยเว็บ public ยังใช้ได้ |

ก่อนเปิดจริง server ต้องตรวจทุกหน้า/API/ไฟล์ แม้เดา URL ได้, ใช้ HTTPS + cookie ที่เหมาะสม + CSRF/rate limit, ไม่ให้หน้าหรือ API auth ถูก cache รวม และไม่ให้แก้ role ผ่าน profile payload โค้ดที่ส่งถึง browser ย่อมอ่านได้ จึงเก็บการตรวจสิทธิ์/นับคะแนนไว้ฝั่ง server และตรวจ build ไม่ให้ secrets หลุดไป client

**ให้ทีมยืนยันก่อนทำ:** Google account ประเภทที่รับเชิญ, ผู้ดูแลบริการ/owner สำรอง, แต้มจริง/ต้องใช้ครบไหม/แก้บัตรก่อนปิดได้ไหม/งดออกเสียง/โหวตตัวเอง/กรณีเสมอ และระยะเก็บข้อมูลสมาชิก/คะแนน/audit/backup การระงับหรือลบบัญชีต้องไม่ทำคะแนนย้อนหลังหายโดยไม่ตั้งใจ

## 6. อะไรเป็น public / private

เอกสารนี้และภาพรวมอยู่ public ได้; schema/ขั้นตอนปฏิบัติ/คู่มือกู้ระบบละเอียดให้เขียนใน private repo เมื่อเริ่มทำ ห้ามเผยรายชื่อจริง คะแนนรายคน backup token หรือ resource credentials ใน public PR/Issue การซ่อน doc ไม่แทนการตรวจสิทธิ์ และ GitHub ไม่มีสิทธิ์ private เฉพาะไฟล์ใน public repo

**สถานะงานนี้: แผนเท่านั้น** ยังไม่สร้าง private repo/ฐานข้อมูล/หน้าใหม่ ไม่เปลี่ยน DNS หรือ deploy ใช้แผนนี้แทนแนวทางเดิมที่ย้ายเว็บหลักทั้งเว็บไป Worker
